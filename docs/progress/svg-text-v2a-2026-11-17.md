# SVG text, V2a: layout and text DOM positions (17 November 2026)

SVG lane, V2a (RFC 0009 V2; plan approved by the parent session on 17 November 2026).

V2a lays out `<text>` and `<tspan>` and gates character positions exactly, through the SVG text DOM
APIs, separately per OS. Glyph painting and its pixel cases come next. They depend on the engine's
T1 (a `div-text` API for positioned glyph runs), so they stay named gaps until T1 lands. `getBBox`
needs ink bounds and is V2b.

## What landed

- **`div_svg::text`** (`crates/div-svg/src/text.rs`):
  - **Model:** `TextSpan` and `TextStyle` trees; `TextFont`, which describes the font at the
    scaled size.
  - **`layout`:** returns a `TextLayout` of fragments, one per text item, in scaled space.
  - **Queries:**
    - `start_position`, `end_position`, `extent` and `computed_text_length`;
    - the item rotation, per fragment.
  - **Ported from Blink's BSD files:**
    - the layout algorithm (`svg_text_layout_algorithm.cc`);
    - the query mapping (`svg_text_query.cc`);
    - item character bounds (`fragment_item.cc`, `LineLeftAndRightForOffsets`).
  - **Clean-room, from SVG 2 and black-box observation** (the Blink originals are LGPL):
    - resolving `x`, `y`, `dx`, `dy` and `rotate` per addressable character;
    - white-space collapsing across elements;
    - the scaling factor and scaled font;
    - baselines and `baseline-shift`.
- **Dependencies:**
  - `div-svg` now depends on `div-text`, and on `div-style` for `FontFamilyList`, to shape text.
    Neither depends back on `div-svg`, so there is no cycle.
  - `docs/v02/generated/dependency-policy.json` is regenerated. Its only change is the lockfile
    hash: the policy has no crate-graph section, and no other check covers the crate graph.
- **`tools/svg/text_corpus.py`:** 131 cases at device scale 1 and at real-zoom scale 2
  (`--force-device-scale-factor`), with vendored Geist and Inter (OFL).
- **Fixtures:** `tests/fidelity/fixtures/svg-text-v1/`:
  - `positions-windows.json` and `positions-linux.json`, from pinned CfT 147.0.7727.50;
  - `known-gaps.txt`, which now has an `<os>` column.
- **`crates/div-svg/tests/text_corpus.rs`:** compares every number exactly, as f64. It fails on an
  unlisted difference, on a changed count and on a listed case that is now exact.
- **`tools/svg/licence_audit.py`:** the audit TSV now also covers the header-only audit of
  `core/layout/inline`, `core/paint/text_*` and `platform/fonts/shaping`.

## Named gaps

Every gap below has an owner. `div-svg` works around none of them (porting principle). The position
gaps are listed per OS in `tests/fidelity/fixtures/svg-text-v1/known-gaps.txt`, and the test fails
once a listed case becomes exact. The pixel gaps apply to glyph painting, which is not in this PR;
the text pixel set lists them when painting lands.

### Positions (gated in this PR)

- **T3. Glyph advances (engine lane, `div-text` shaping):**
  - Chromium truncates Skia glyph advances to 1/65536 px; `div-text`'s SkShaper path rounds them.
  - Affects Windows only: 7 case-scales, 3 to 5 numbers each.
  - Experiment: with T3 and T4 applied in the SVG layout, all 24,056 Windows numbers are exact.
  - The experiment code was removed.
- **T4. Font size (engine lane, `div-text` font cache and platform font):**
  - Chromium shapes at the size truncated to 1/100 px of the device size; `div-text` uses the exact
    size.
  - Affects 6 case-scales on Windows and 4 on Linux, 16 to 28 numbers each. All of them are
    transforms that give a fractional scaled size.
  - Experiment: truncating the size alone made all 24,056 Linux numbers exact.
  - HTML text measures the same way in Chromium (sizes 25.29 to 25.299 px give identical widths),
    so the fix reaches beyond SVG.

The engine lane has sized both as fillers, each its own PR with a full census, in the order T1, T4,
T3. Each fix removes its gap lines in the same change.

### Pixels (glyph painting, next PR)

- **T1. Positioned glyph blobs (engine lane, `div-text`):**
  - SVG text paints each fragment as its own glyph run, at layout positions, under the fragment's
    transform. `div-text` has no API for a blob at given positions over part of a shaped run.
  - The engine lane is adding `ShapeResult::to_positioned_text_blob`: a character range, one
    placement per glyph, the raster policy and the device scale. It takes positions only.
  - Until it lands, every text pixel case is a named T1 gap.
  - Rotation was measured on Windows, CfT 147, in 10 cases at 1x and 2x (a scratch probe, not
    committed). A positioned run per fragment under a canvas rotation and an RSXform blob paint
    byte-identically. Glyph ink lines up with Chromium's: identical bounds, best alignment at zero
    offset. So T1 needs no rotation API.
- **Windows LCD text (fidelity lane, font edging):**
  - Windows Chromium paints this SVG text, in Geist and Inter, with LCD subpixel anti-aliasing.
    That includes `rotate` glyphs and text rotated by its CTM.
  - `div-text` resolves these web fonts with `AntiAlias` edging, so every `TextRasterPolicy` gives
    grayscale. Grayscale differs from Chromium by up to 154 per channel.
  - With LCD forced on (an RGB-stripe surface), every case is within 16 per channel, controls
    included. That residue is a tone (gamma or contrast) difference, not geometry. HTML text in
    these faces likely has the same gap.
  - The fidelity lane owns Windows LCD text; the parent routes it. Until it is fixed, the Windows
    text pixel cases are named gaps owned by that work, even after T1.
  - Whether Chromium phases rotated LCD glyphs the way `div-text` phases unrotated ones can only be
    measured once LCD is available. With plain Skia positions, rotated cases stayed within the same
    16-per-channel bound as the controls.
- **Linux pixels:** not measured yet. Linux uses the Fontations outline path.

## What the corpus taught (Chromium 147, black box unless marked BSD)

- **Items:**
  - A text item covers one element's text in one font, and is split before every character that
    has `x`, `y`, `dx`, `dy`, `rotate` or starts an anchored chunk.
  - Its inline size is `ceil` to 1/64 px of its summed advances. Offsets accumulate in layout
    units.
- **Shaping:**
  - Consecutive text in the same font is shaped as one run, so kerning crosses `tspan` and `dx`
    boundaries.
  - Shaping breaks only at chunk starts.
  - A ligature's advance is split evenly among its characters.
- **Scaling factor:**
  - The scaling factor is `sqrt((a² + b² + c² + d²) / 2)` of device scale × CTM.
  - Font size, letter-spacing and word-spacing are scaled by it.
  - The `opsz` axis follows the unscaled size: Inter at scale 2 shows it.
- **Lengths:** length lists parse as CSS does (double, then float), and `em` resolves with a float
  multiply.
- **Baselines** use integer ascent and descent:
  - `middle` uses the x-height, rounded to 1/64 px;
  - `central` is the midpoint;
  - `baseline-shift` sub and super are ±(ascent + descent) / 2;
  - length shifts truncate to 1/64 px and accumulate over ancestor `tspan`s.
- **Queries (BSD port):** each item's character bounds are `floor64` and `ceil64` of the caret
  positions. A query maps them through the item's rotation, computed in double precision, and
  then scales them by 1 / scaling factor in float.
